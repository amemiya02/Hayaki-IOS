# Use Android Hayaki as the acceptance baseline for native iOS

Hayaki on iPhone and iPad will implement the learner-visible behavior of the [Android baseline](https://github.com/amemiya02/Hayaki/tree/0f5dc353fb424751d74ba7d315457b62d95348a7). Keep the unpatched Anki core, SwiftUI screens and the web view for card content and previews. The previous release limits on statistics, deck options and other features are superseded by the full Android inventory.

Self-hosted sync and AnkiWeb are both product requirements. Existing self-hosted profiles retain their destination and credentials. Use upstream’s unmodified sync implementation and default destination for AnkiWeb, following the Android project decision. In a discussion about an AnkiDroid fork, Anki’s author said syncing should be fine when the sync code is unmodified and causes no service problems, and recommended a distinct app name. Hayaki retains its own identity. [Author’s reply](https://forums.ankiweb.net/t/would-it-be-bad-to-upload-an-ankidroid-fork-to-the-play-store-for-free/67022/20) · [Android decision](https://github.com/amemiya02/Hayaki/blob/0f5dc353fb424751d74ba7d315457b62d95348a7/docs/adr/0001-own-fork-no-upstreaming.md)

Verify live service behavior with a dedicated account and keep routine integration tests on a self-hosted server. This supersedes the product scope in [ADR 0002](0002-no-ankiweb.md) and the subset in [ADR 0004](0004-all-native-screens.md).
